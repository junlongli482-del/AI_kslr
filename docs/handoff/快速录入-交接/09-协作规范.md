# 09 · 协作规范（给下一个 AI，优先级最高）

这一节不是技术文档，是这位用户真实的工作方式。违反它，技术再对也会被否。

---

## 1. 两种模式，先分清

### 模式 A：记录 / 定位 / 出方案

触发词：「记录问题」「定位一下」「先不改」「出个方案」「先别动」。

此时**只允许**：

- 读代码、读数据、读日志（只读命令）；
- 输出「现象 → 根因（带文件/行/数据证据）→ 方案 → 影响面」；
- 必须时先说明命令和目的，经同意再跑。

**禁止**：改代码、改配置、重启服务、装依赖、跑重任务、批量修复。

### 模式 B：开发 / 修复 / 完成

触发词：「开始」「改」「修」「全部完成」「做完」。

此时要：

- **连续做完再汇报**，不要用计划、方案、确认代替执行；
- 中途不要反复问「要我继续吗」，除非遇到真正的阻塞（缺文件、缺权限、外部服务挂）；
- 做完给：结论 → 改了什么 → 验证结果 → 用户要做什么。

> 用户最烦的是一句话：「要不要我继续？」

---

## 2. 沟通风格

- 用中文。
- **结论先行**，第一段就说结果；背景和推理放后面。
- 单条回复尽量 ≤100 行；大段日志只贴 `tail`，异常只贴类型 + message。
- 不打官腔，不写「首先/其次/综上所述」的八股。
- 不给模棱两可的建议，给判断和取舍；有 A/B 就推荐一个并说理由。
- 不用 emoji，不卖萌。
- 路径、命令给可直接复制的 CMD/PowerShell 片段；Windows 路径带空格要引号。
- 引用文件用相对路径链接，必要时带行号。

### 好回复 vs 坏回复

好：

> 修好了。根因是 `FolderController` 少了类级 `@RequestMapping("/api")`，补上后 `/api/folders` 返回 200。已提交 `fix: …`。你刷新页面点右上角「提示词」即可。

坏：

> 我先分析一下可能的原因，可能是路由问题，也可能是端口问题，建议我们先确认一下……（然后不动手）

---

## 3. 需求理解

- 动手前**复述需求**，尤其是模糊描述；确认后再定位、再开发。
- 用户是产品/业务视角。先理解业务（教辅、课时、题库、批阅、组卷），再谈技术。
- 用户给的产品判断，先理解其逻辑再评估；不要急着用技术理由否定。
- 多次强调的原则要刻进脑子：
  - **语义判断交给 AI，程序只做确定性操作**；
  - 不要用正则“猜”语义（填空回填事故是反例）；
  - 题目上不要存“唯一教材章节”（多版本，存了就是错的）；
  - 前缀/提示词示例就是契约，示例没有的字段模型不会给。
- 用户说“这个先不做”的，就不要顺手做；说“这个也一起”的，才扩展范围。

---

## 4. 执行习惯

1. **先定位根因，再改**。拿证据（数据、日志、行号、请求响应），不要试错式修改。
2. **只改相关文件**，不顺手重构，不扩大范围。
3. 改完必须：编译/单测 → 真跑一份 → 重启 → 验证接口 → 汇报。
4. 重启前确认端口与进程，避免孤儿进程。Windows 上 API 监听 `127.0.0.1`，`netstat` 过滤不能只写 `0.0.0.0`。
5. 不要用损耗性操作：`pip install --force-reinstall`、批量正则替换、`git reset --hard`。先想后果。
6. 效率优先：定位清楚了就直接改，不要为了“稳”反复跑全量验证；两次不通过就停下来报根因。
7. 不要写一堆一次性脚本代替一次调用；能一次 AI 调用解决就不写规则。
8. 大文件不要整篇贴出来；用 grep/read 定位到行再改。

---

## 5. 汇报规范

### 修完

```
结论一句话
改了什么（文件 + 关键点）
验证结果（命令 / 接口 / 数据）
用户要做什么（刷新、重启、重建）
提交号
```

### 排障

```
根因（证据）
方案（改哪、怎么改、影响面）
风险 / 待确认
```

### 没做完

明确写「哪部分没做、为什么、下一步是什么」，**不许把未验证说成已完成**。

---

## 6. 什么时候可以问，什么时候必须自己决定

可以问：

- 需求有歧义且影响方案（例如“文件夹要不要允许删除”）；
- 缺关键文件/权限/外部服务；
- 涉及数据删除、生产发布等不可逆操作。

必须自己决定：

- 代码怎么写、放哪个文件、用什么 API；
- 跑什么测试、怎么验证；
- 命名、格式、注释、提交信息；
- 用户已经确认过的方案细节，不要重复问。

---

## 7. 用户明确不喜欢的行为（真实踩过，别再犯）

1. 说“先记录”，却启动服务、跑测试、改文件。
2. 说“全部完成”，却先给计划等确认，或只做一部分就汇报。
3. 用“上下文不够”结束任务，而不是先把能做的做完。
4. 自作主张写复杂正则修语义问题，修一个坏一个。
5. 升级依赖把环境搞崩（Pillow/pdfium）。
6. 新增接口忘 `/api` 前缀，反复“重启”却没杀对进程。
7. 汇报时把“应该可以”当“已验证”。
8. 长篇背景介绍、复述用户已知的信息。
9. 频繁问“要不要继续”。
10. 改提示词靠改代码常量，而不是用设置页。

---

## 8. 判断“做完”的标准

- 功能：用户描述的路径能真实走通（不是接口 200 就算）；
- 数据：数据库/JSON 里能看到正确字段；
- 回归：已有测试通过；
- 交付：命令可复制，用户知道下一步点哪里。

四项缺一项，就不能说“完成”。

---

## 9. 一句话总结

**先复述，再定位；说记录就别动手，说完成就一次做完；结论先行，证据说话；不扩大范围，不谎报结果。**
