## 4. 数据流

```
上传 → MinerU(本地/云端) → normalize（页图、块坐标）
     → 栏数独立调用（AI，只发页图，与几何冲突时复判）
     → 结构化（AI，题框、题组、小问、excluded_block_ids）
     → 答案提取 → 答案匹配（AI）→ 填空匹配（AI，学生用书）
     → 打标（AI，前缀：题型/子形态/知识点/难度 0-1）
     → 题框/裁图 → 审核页 → 审核入库（题库/试卷库）
     → 导出 /export/papers/{id}（含 blank_label、folder_path）
```

关键约定：

- 题目**不再存教材版本/册**；章节由下游按「知识点 → kp_position」现算。
- 题组括号导出带 `blank_label`（如 `9-1`）、`question_number`、`subquestion_number`。
- 填空用 `{{blank}}` / `{{blank:n}}`，答案在 `questions[].blanks[].answer`。
- 题框坐标为 0–1 归一化 + `page_index`。
- 语义判断交给 AI；程序只做几何、校验、渲染、保护（用户明确要求）。

## 8. 常见故障与处理

1. **AI 服务 1003 假死 / 端口在但没响应**
   - 先看是否有孤儿进程：`Get-CimInstance Win32_Process -Filter "Name='python.exe'"`；
   - reload 模式下 worker 崩了会留 reloader 占端口；现配置为无 reload。
2. **AI 启动即崩，`_imaging` 或 pdfium DLL 0x4551**
   - Pillow 固定 10.4.0；pypdfium2 固定 4.30.0；
   - 不要用 `pip install --force-reinstall pypdfium2`（会顺带升级 Pillow）。
3. **1002 重启无效**
   - API 监听在 `127.0.0.1:1002`，netstat 过滤必须包含 127.0.0.1；
   - 杀进程用 `netstat -ano | findstr :1002` 取真实 PID。
4. **新增 Controller 404**
   - 现有控制器类上有 `@RequestMapping("/api")`，新控制器必须同样加。
5. **本地 MinerU 不健康**
   - `local_available:false` 常见于刚重启、模型加载中；等 40 秒；
   - 健康检查超时 1 秒，加载期间会误报。
6. **Docker 拉镜像失败**
   - Docker Hub 被墙：`docker pull docker.m.daocloud.io/library/<image>` 再 tag。
7. **Vite 启动报 Rollup 原生模块被 Application Control 拦截**
   - 让用户在 Windows 安全中心放行，或删 `node_modules` 重装。

## 9. 如何与我协作（重要，先读这一节）

### 沟通方式

- 用中文；**结论先行**，再给依据；单条回复尽量不超过 100 行。
- 不要贴大段日志：只看 `tail`，异常只留类型 + message。
- 不要用「建议 / 可以 / 或许」糊弄，给判断和取舍。
- 用户说「记录问题、先不修改」时：**禁止改代码、改配置、重启服务、跑验证命令**，只做只读定位，输出「现象 → 根因 → 方案 → 编号」。
- 用户说「开始 / 全部完成」时：连续做完再汇报，**不要中途用计划代替执行**，也不要反复问「要我继续吗」。
- 不要拿「上下文不够」当借口；确实做不完就明确说「哪部分没做」，不许把未完成说成完成。

### 需求理解

- 动手前先**复述需求**，特别是模糊描述；确认后再定位。
- 用户是产品/业务视角：教辅、课时、题库、批阅流程比代码细节重要；先理解业务，再评估技术。
- 用户反复强调的原则要记住：**语义判断交给 AI，程序只做确定性操作**；不要用正则做“猜语义”的事（填空回填事故就是反例）。
- 用户不喜欢为一点点功能写一堆脚本；能一次调用 AI 解决就不要写规则。

### 执行习惯

- 先定位根因、拿证据（数据、日志、行号），再改；不要上来就试。
- 只改相关文件，不扩大范围；不要“顺手重构”。
- 改完必须：编译/单测 → 真跑一份 → 重启服务 → 验证接口 → 汇报结果。
- 重启前确认端口与进程，避免留孤儿进程；Windows 上尤其注意 127.0.0.1 监听。
- 不要用损耗性命令（force-reinstall、批量替换）处理依赖，先确认后果。
- 交付命令必须是可直接复制的 CMD 片段。

### 回复结构

- 修完：一句话结论 + 改了什么 + 验证结果 + 用户要做什么。
- 排障：根因（带证据）+ 方案 + 影响面 + 待确认点。
- 不要长篇背景介绍；不要复述用户已经知道的东西。

### 用户明确不喜欢的行为（本会话真实踩过）

1. 用户说“先记录”，我却启动服务、跑测试、改文件。
2. 用户说“全部完成”，我先给计划、等确认，或只做一部分就汇报。
3. 自作主张把防护逻辑写成复杂正则，结果修一个坏一个。
4. 依赖升级把环境搞崩（Pillow/pdfium）。
5. 新增接口忘了 `/api` 前缀，反复“重启”却没杀对进程。
6. 用“上下文不够”结束任务，而不是先做能做的部分。
7. 汇报时把未验证的东西说成“已完成”。
