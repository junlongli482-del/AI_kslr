## 二、当前超时与渠道逻辑：源码事实

代码：`apps/ai/core.py` 的 `LLM.json`，本次核对约411–430行。

- 当前只依次尝试 LOW、STABLE，stable_first 时顺序反转；不是同时调用。
- 当前 `httpx.Client(timeout=httpx.Timeout(300, connect=25))`：读取超时300秒，建立连接25秒，其他未单独指定的超时也继承300秒。
- 当前请求不是流式请求。ReadTimeout 是等待接收数据超时；不等于已经证实模型停止计算或题目处理不了。
- HTTP 524 是渠道返回的HTTP错误，通常意味着代理/网关等待上游超时。提高本地等待时间不修改供应商的网关等待上限；不能承诺改为1800秒就消除524。是否确由Cloudflare及其实际阈值需查看供应商响应证据。
- 两个现有GPT渠道按用户提供信息使用相同入口与模型、不同密钥，不能据此当作独立基础设施。
- 用户给出的多个样例证明存在失败，但不能据此编造整体失败率。下轮要按阶段/渠道统计成功率、时延及错误类别。

参考：HTTPX官方 `https://www.python-httpx.org/advanced/timeouts/`；Cloudflare官方524说明 `https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/`。本次检索未确认用户给出的DeepSeek模型标识可用；接入时需供应商实际地址或其模型列表。

- 并发对比：共享已完成OCR；每个模型使用相同输入、提示词及约束，独立结构化、答案流程、结果、缓存与费用明细。缓存键包含渠道、模型、输入摘要、提示词/协议版本，避免拿同一个缓存冒充多个模型的结果。

- 重试复用已完成阶段，记录累计成本；禁止无上限重试造成无限请求。重试策略与持续等待是不同事项。

## 三、目前图片处理链路

### 1. MinerU产物归一化

代码：`apps/ai/core.py` 的 `normalize` / `enrich_asset_metadata`，约135–230行。

- 读取原始MD、图片包、middle.json，middle缺失时使用content_list.json。
- 图片保存 `width_px` / `height_px`：这是裁出图片文件本身的像素宽高，不等于它在PDF上占据的宽高。
- 页面保留页面尺寸；内容块保存 `page_index`、归一化 `bbox=[x0,y0,x1,y1]`、顺序与文本。
- content_list路径可提取图片bbox；middle路径当前递归收集image_path，但没有逐个提取嵌套图片span的精确bbox。缺失坐标时使用外层块bbox补齐，所以不能保证每张图坐标都是单图精确位置。
- 同行分组、排列顺序、间距、重叠和“被拆分的同一张图”尚未形成完整的结构化布局关系。

### 2. 给AI的内容

代码：`compact_document`，约505行。

当前发送：完整MD；图片URL及已有的bbox、页码、裁图像素宽高；块ID、坐标、类型和短文本锚点。

当前没有显式传入页面尺寸表、单图在PDF里的物理宽高、布局组和明确间距。消息使用文本JSON，没有直接发送多模态图片内容。旧阶段缓存还可能复用未包含新增images字段的输入结果；不是所有历史题目都经新版输入处理。

### 3. 要求AI输出的内容

代码：`STRUCTURE_PROMPT`，约484行。

当前要求题干、选项、小问、块ID、属性，并要求保留URL、同行多图写在同一Markdown行。

**当前提示词没有强制要求AI输出逐图宽高、布局组、行列、间距等完整image_layout。** 虽然数据模型有image_layout字段，现有程序主要在AI之后由代码补算它。这不符合此前用户要求的完整“源数据→AI布局JSON→渲染”闭环，属于实现缺口。

### 4. 后处理和编辑器渲染

代码：`apps/ai/core.py` 约625–650行；`apps/web/src/repair.ts` 约24–29行；`apps/web/src/App.vue` 约183行；`apps/web/src/components/QuestionEditor.vue` 约49行；`apps/web/src/style.css`。

- 后端用图片bbox宽度除以找到的题目region宽度，计算百分比，没有匹配region时用0.45页宽。
- 前端修复逻辑又算一次相同比例，会覆盖已有render_width_pct。
- 图片选项全部带图片时，启发式最多分4列，而不是完整读取原卷布局；每列宽度是编辑区的1/4等比例。
- 编辑器用widthPct生成内联CSS百分比。存在此属性时CSS取消最大高度限制。
- 当前可以保存widthPct，但没有供用户操作的图片缩放手柄/尺寸控件。

## 四、忽大忽小的具体原因

### 图片过大

如果找到的region本身就是图片裁切框，图片宽度/region宽度接近1，于是被算成100%。该100%会应用到整个题干编辑区，取消高度限制后，细长弹簧图会被放得非常大。源码存在此确定风险；截图可见第8题弹簧图异常放大，具体记录的数值尚未逐任务读取确认。

### 选项图片过小

图片百分比先按整题/页面宽度换算，再放进已缩成1/4宽度的选项格，发生重复缩小。例如本应占整题20%的图，在1/4宽格子里又用20%，最终只剩整题5%。这是当前参考系混用导致的风险；截图第3题四个选项图比下方原卷图小很多。

### 坐标不精确与双重计算

外层块bbox代替单图bbox会使比例不准。后端与前端各自计算，加上CSS和选项容器共同作用，没有统一的尺寸来源/覆盖优先级，所以不是单加一个max-width就能完整解决。

### 甲、乙图片链接失效

截图第三张可见两个破图标记“甲”“乙”和一张放大的有效图片。破图涉及资源引用/地址解析，尺寸换算不能解释它。可能是无效或相对引用未被替换，同时补图逻辑追加了有效原图，但未移除/修复无效引用。该解释待逐任务核对实际URL和资产响应，尚未确定根因。

- 相邻拆图支持按原页小间距并排；必要时联合裁切为一图，保留源图来源，不仅用Markdown同一行假定拼接完成。
- 题干、选项、答案、解析使用同一布局协议与渲染实现。只修题干不能关闭问题。
