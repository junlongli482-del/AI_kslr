# 用户反馈：图片排版、并发处理与公式编辑

记录日期：2026-10-15。来源：用户提供的7张截图及本轮文字反馈。

状态：已记录，待开发与回归验证。本次记录不等于这些问题已经修复。原《验收报告》中的代表场景通过，不能覆盖本次新化学试卷场景。

本记录按需求梳理方式区分：用户已明确的期望、截图现象、源码已确认的限制、开发建议。建议中的协议与实现选择尚未落地；不把“可能是MinerU切成两张图”直接写成已经定位的根因。

## 1. QE-FB-001：图片渲染必须依据原页几何关系

优先级：P1，影响题目语义完整性。涉及：原包归一化、图片分组、内容编排、编辑器和题库预览。

### 用户已明确的要求

- 原卷一幅图即使被识别工具拆为多张小图，也应支持合成或作为同一个布局组展示。
- 原卷两张图并排、相邻间隙很小或没有间隙，渲染时应保留这种关系，而不是默认每张图单独一行。
- 图片宽高、原页位置、相对大小、间距是排版依据；不能仅凭MD里图片先后顺序决定显示。
- 同一题在审核编辑器、预览和入库后展示中，应具有一致的图片布局。

### 截图中的两个复现样例

**样例A：化学第9题，抑制剂与蛋白酶体的反应图。**

图1是当前编辑器：结构图上下分开，图间出现“X、Y”“Z”文字。图2是原卷区域：结构和反应关系在同一行，包含左侧结构、中间结构及箭头、右侧复合结构。当前展示的语义关系与原卷不同。

需要进一步核对：原包究竟切成几个图片资产；中间结构、箭头是未识别、没有选入题干，还是被裁进其他图片。不能只把已显示的两张图片放一起就宣布修好，必须确认整段反应关系完整。

**样例B：化学第12题，淀粉结构的两幅示意图。**

图3中两图上下排列，图4原卷为横向组合，文字与图穿插，显示相对大小不同。这里不能把所有同一行的图无条件合成一张：还需保留两图之间“Y_p表示”等文字、标点与题干的阅读顺序。

证据见本目录下 screenshots/feedback-20261015 的01～04图片。图片只证明渲染偏离原卷；MinerU分图是否为唯一根因尚未确认。

### 源码确认的当前限制

1. core.normalize 保留图像像素尺寸，content_list分支补充bbox、page_index，但middle分支元数据不完全一致。
2. compact_document没有把完整asset_metadata和逐图排版关系发给AI，只提供MD和带坐标的块摘要。
3. normalize_question_content及compile_result的同行处理主要检查相邻图片页码和顶边差，小于0.035时把图片放在同一MD行；没有完整判断同来源、横向间距、共同基线和图文混排。
4. QuestionPreview与QuestionEditor没有读取image_layout来逐图设定基于原页的宽度和间距。只把MD图片放到同一行仍不能保证真实比例与近零间距。
5. 目前没有正式image_group节点、图片重组工具或“同一幅被拆开的图”的结构化标记。

源码位置：apps/ai/core.py中的normalize、compact_document、normalize_question_content、compile_result；apps/web/src/render.ts；components/QuestionEditor.vue、QuestionPreview.vue。

### 建议的处理链路（待实现）

**第一步：先建立可靠几何信息。** 每张图片关联document_id、page_index、原始block_id、归一化bbox、像素尺寸和来源资产URL；目录分支统一到相同字段，不能仅用同页码推定来自同一页。

**第二步：判断布局关系。** 在同文档、同物理页、同题内，结合纵向重叠、水平间隙、阅读顺序、共同图注或连线，产生图片组候选。至少区分：

- 单幅完整图；
- 一幅图被切成多个相邻片段；
- 多幅独立图横向并排；
- 文本、图和公式混合的行。

阈值应针对原页坐标或组宽高定义，使用真实样例校准；不能把当前0.035当作最终所有学科通用标准。AI可辅助判断语义组合，但图片是否相邻、原始间距是多少，应由坐标计算而不是让AI猜数字。

**第三步：被拆开的同图优先从原页联合裁切。** 如果确认属于一幅图，取覆盖相关原区域的联合范围，从原页生成复合图，保留箭头、线条和未进入OCR图片资产的局部文字。它比任意贴合两张识别裁图更容易保持原始关系；须检查联合范围是否夹入无关题目或内容。原资产保留，并记录成员、联合bbox和reconstruction_source。

**第四步：独立图与图文行保留结构。** 独立图不要为了同行就焊成一个不可编辑图片；建议有layout_group和有序item，可包含image、text、math。根据原bbox计算相对宽度、位置和间距，窄屏整体等比缩放或提供横向查看，避免自动上下换行改变反应结构。

**第五步：一致渲染和编辑。** 图片组需由编辑器节点、预览和库内展示共同支持，编辑后保存布局数据。给用户合并、拆组、调间距和恢复原布局的能力。保留Markdown兼容表示，但不能靠一次Markdown换行承载全部几何信息。

协议示意（建议，非现有Result Schema）：

~~~json
{
  "layout_groups": [{
    "id": "lg-demo-1",
    "document_id": "doc-demo",
    "page_index": 0,
    "kind": "fragmented_figure",
    "bbox": [0.1, 0.4, 0.7, 0.6],
    "member_asset_urls": ["/api/assets?key=demo%2Fa.png", "/api/assets?key=demo%2Fb.png"],
    "member_block_ids": ["doc-demo-b3", "doc-demo-b4"],
    "render_asset_url": "/api/assets?key=demo%2Freconstructed.png",
    "reconstruction_source": "original_page_crop",
    "review_status": "pending"
  }]
}
~~~

### 验收标准

- 化学第9题的全部反应结构和箭头可见，保持左右顺序、相对比例及小间距；没有丢失中间结构。
- 化学第12题能保留两图相对大小和图间文字，“X_m表示 / Y_p表示”等各自对应正确，不用无依据的新段落割裂图文。
- 不同文档相同page_index的图片不会被归为同组；跨栏、跨页独立图不会被错误拼接。
- 审核编辑、题目预览、保存刷新、入库详情四处一致；人工调整布局后不会被自动编排覆盖。
- 留存原卷与渲染对照；除结构合法外，人工核对化学连线、箭头、上下标和图注。

## 2. QE-FB-002：支持多个任务及独立API调用并发，避免提交后滞留

优先级：P1。涉及：任务创建、调度、上传启动状态、外部请求限制、恢复。

### 用户已明确的要求

一个任务运行时可以提交其他任务；API调用可以同时执行，不能因为系统固定单任务限制而迫使用户等前一个任务结束。用户上传后希望处理自动推进。

证据：图5，已有数学任务处理中，两条“化学1”显示待处理、阶段待上传。重复任务的产生原因需核对日志，不能单凭截图断言用户重复点击或自动重试。

### 源码确认的当前行为和可能故障路径

- Python默认QUICK_ENTRY_MAX_CONCURRENCY=1。超额任务直接409，没有持久化等待队列。
- 前端顺序执行“创建任务→上传文件→start”。start出错时已有数据库任务不会撤回。
- Java在Python接受start后才写running；此前失败则任务可能保留uploaded。
- 前端把uploaded显示为“待处理”；进度页仅对failed和interrupted显示恢复按钮。uploaded因此可能没有有效的继续启动入口。
- 每个任务内的文件识别和题目结构化也按循环串行处理；独立文件并未自动并发。

因此这是系统当前限制及任务生命周期缺口，不是“API本来只能一次调用”。截图中的具体记录是否因409、上传失败或其他原因留下，要以任务文件记录、Python/Java日志为准。

源码位置：apps/ai/main.py中的start、process；apps/ai/core.py中的compile_result；Java TaskService.start；App.vue中的createTask、statusName和进度页。

### 建议实现方向（待实现）

1. 多任务并发：配置worker数量或任务执行槽位，不把默认1当作产品约束。并发目标由接口实际限流与本地资源确定，开发验证至少能观察到两个不同任务同时推进。
2. 分层并发：任务级、文件识别级、模型请求级分别控制；同任务中独立文件的MinerU与结构化可并发，答案提取可按依赖并行。全局匹配要等题目和答案候选就绪，不能打破依赖强行并发。
3. 确认启动：采用可恢复的“上传完成 / 已提交 / 正在处理 / 等待资源 / 失败”状态，启动失败保留原因和继续按钮。容量满时任务应被可靠接纳和后续调度，不能留下无恢复入口的uploaded任务。
4. 有限调度：只有实际达到资源或供应商限制才等待，并自动继续；这不等于永不出现等待状态，也不等于无限并发。等待须解释原因，不让用户再次新建重复任务。
5. 请求治理：按MinerU和两个模型渠道设置独立信号量与429退避，保持渠道回退；请求重试不能重复造任务或重传已经识别的源文件。
6. 共享状态：为并发日志、calls缓存、token预算计数与结果聚合建立线程安全或事务策略。不能只改环境变量就把文件循环、缓存和预算的竞态视为全部解决。
7. 创建幂等：保留当前提交task_id；失败后恢复该任务，而不是每次点开始都创建一个新任务。前端已有busy按钮仍不足以覆盖失败后的重复提交。

### 验收标准

- 连续提交两份独立资料，两任务可同时处于真实处理中，各有独立阶段进度，不等待前任务全部结束。
- 多文件并发完成后保留输入顺序、稳定ID和正确文档来源；共用答案仍可全局匹配。
- 超限、429、断网或启动失败时，任务状态和操作入口可解释、可恢复；不存在只能重新创建的“待处理”孤立记录。
- 同一提交重试不造重复任务，不重复支付已缓存阶段；一个任务失败不污染其他任务。
- 并发日志可观察外部请求时间区间的真实重叠，不能只把状态同时设为running充当并发证据。

## 3. QE-FB-003：公式编辑采用WPS / Word式结构模板交互

优先级：P1，影响普通教师可用性。涉及：QuestionEditor公式弹窗、MathLive交互封装、公式往返序列化。

### 用户已明确的要求

参考截图7的WPS / Word公式工具栏，采用分数、上下标、根式、积分、括号、矩阵等分类模板操作。当前弹窗与虚拟键盘交互不好用，不能仅因“可输入LaTeX”或“有可视化框”就认为体验合格。
LaTeX源码编辑必须保留，不能被MathLive或MathType的可视化界面取代。用户需要能够查看、直接修改和复制LaTeX。

用户提到的“M开头公式编辑器”很可能是MathType；未获得用户对名称的最终确认。此处仅记录为候选交互参考，不视为已经选择采购或接入该产品。具体产品的接口、授权和格式支持范围尚未核实，需在选型时查官方资料。

### 当前现象与边界

图6中公式弹窗、输入区、重复预览与屏幕底部键盘同时出现。截图能确认键盘占较大屏幕区域；是否覆盖某些操作仍需不同屏幕高度验证。

当前MathLive只提供单个math-field及其键盘入口，外层没有WPS式分类结构模板栏。公式底层已经用LaTeX保存，这一点可以继续沿用，UI改善不需要把公式保存成图片。

### 确认后的编辑模式

公式编辑最终提供三个入口：

1. **可视化基础模式**：MathLive，适合本地部署和常用公式快速修改。
2. **专业模板模式**：MathType风格 / MathType集成，适合接近WPS、Word的分类公式工具栏。
3. **LaTeX源码模式**：直接查看和编辑原始LaTeX，作为高级编辑、兼容性修复和最终可追溯入口。

三种入口不产生三套独立内容。公式以LaTeX为主值，编辑器只是不同的操作界面：

~~~json
{
  "latex": "\\frac{a}{b}",
  "mathml": "<math>...</math>",
  "source_editor": "mathlive|mathtype|latex",
  "review_status": "pending"
}
~~~

其中 `latex` 是题库主存储和跨编辑器交换格式；`mathml` 只作为可选渲染 / 转换缓存，不能取代LaTeX。编辑器不能写入无法再次导出的专有格式作为唯一数据。切换模式时，必须先把当前内容转换回统一LaTeX，再交给另一个编辑器打开。

### 建议交互方案（待实现）

- 可视化模式默认打开，顶部是常见结构分类，不要求教师先理解LaTeX；用户可以随时切换到专业模板或LaTeX源码。
- 分数、上下标、根式、括号、积分、求和、函数、极限、矩阵分类中提供可点击的模板缩略图，而非只列命令名称。
- 点模板在当前光标插入带占位槽的结构，直接进入第一个槽；Tab / 方向键可在槽间导航，支持嵌套与选中内容套入结构。
- 基础数字、希腊字母、关系符与运算符易找到；化学样例覆盖多级下标、上标、电荷和括号外下标。
- 当前公式就地可视化反馈，减少重复占高的预览；保存、取消始终可见，虚拟键盘不遮挡编辑区和操作栏。
- 提供撤销 / 重做、清空、编辑器切换和源码切换，已有公式可再次编辑；取消不改变原稿，保存仍输出LaTeX。
- LaTeX源码是永久保留的正式入口，不成为老师完成普通公式的必要步骤，但不能隐藏或删除。

实现建议：先评估能否用现有MathLive编辑内核提供结构模板工具栏与光标插入能力；不足再对比MathType等候选的实际集成与格式往返。选择新产品前核实授权及服务要求，当前不定采购，不承诺已完成任意OMML / MathML / LaTeX无损转换。

### 验收标准

- 不输入任何LaTeX命令，能完成分式、带上下标表达式、根式、求和及2×2矩阵。
- 能编辑化学式(C₆H₁₁NO₄)ₙ以及带离子电荷的上下标，保存后显示与再次打开一致。
- 可以在光标位置插入、替换选中表达式、修改嵌套槽，支持撤销 / 重做与取消。
- 常用桌面尺寸和窄屏上，键盘展开时仍可操作保存 / 取消，无明显遮挡。
- 公式编辑器、LaTeX内容、题库预览的往返检查通过；不能把仅构建通过作为可用性验收。

## 5. QE-FB-004：记录并显示每份卷子的处理成本

优先级：P1，影响运营核算和后续定价。当前代码只有 LLM 返回的 usage 和调用记录，没有金额字段，也没有 MinerU 费用账本。

### 产品要求

- 每个快速录入任务显示总处理成本；一个任务包含多份试卷时，支持按识别出的 paper 分摊查看。
- 展开查看 LLM、MinerU、本地转换、重试和缓存复用明细。
- 区分 `actual`（按已配置单价和供应商用量计算）、`estimated`（用量或单价不完整的估算）、`unknown`（供应商未提供可核实价格）。
- 保存价格快照，未来改价不改变历史任务成本。
- 缓存命中不重复计费；外部请求失败但供应商返回 usage 或已扣费时保留；未发出外部请求的本地失败不计外部费用。

### 成本明细协议建议

~~~json
{
  "cost_summary": {
    "currency": "CNY",
    "status": "estimated",
    "total": 1.28,
    "by_paper": [{"paper_id": "doc-demo-p1", "amount": 0.64}],
    "by_provider": {"mineru": null, "llm": 1.28}
  },
  "cost_items": [{
    "provider": "llm",
    "channel": "low",
    "model": "gpt-6.1-sol",
    "stage": "structure-doc-demo",
    "document_id": "doc-demo",
    "input_tokens": 12000,
    "output_tokens": 2200,
    "cached": false,
    "unit_price_snapshot": {"input_cny_per_million": 0.0, "output_cny_per_million": 0.0},
    "amount": 0.0,
    "amount_status": "estimated",
    "usage_source": "provider_response"
  }]
}
~~~

LLM费用按 `input_tokens × 输入单价 + output_tokens × 输出单价` 计算。只有 `total_tokens` 时，按配置比例估算并标记 estimated。当前 `calls.json` 已保存阶段、渠道、模型、耗时和 usage，后续应在调用完成时写入 cost_items。
