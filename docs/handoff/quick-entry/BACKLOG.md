### QE-FB-013 / P1 评分标准阶段 Pydantic 校验失败（issues 为对象而非字符串）

- 现象：任务 `ae6b5a7f-7389-4afd-99ca-11e6b219c153`（26秋 地理 选择性必修2 区域发展 中图版 试卷_5-8）在「评分标准」阶段失败：`1 validation error for Result / questions.7.issues.0 / Input should be a valid string [type=string_type, input_value={'type': 'subquestion_blo...}]`。重试多次同样失败。
- 根因：
  1. 结构化输出把第 17 题 issues 写成对象 `{"type":"subquestion_block_missing","message":"…block_ids为空。"}`（`data/tasks/ae6b5a7f-…/llm/structure-d080e50b64ad54453-*.json`）。
  2. `normalize_model_question()`（apps/ai/core.py:677-680）只 setdefault，不收敛类型。
  3. `Question.issues` 为 `list[str]`（core.py:105）且无 validator；最终在 `compile_result` 末尾 `Result.model_validate`（core.py:1372）才校验，所以跑到最后的「评分标准」阶段才报错。
  4. 重试命中同一 structure 缓存 → 同样的对象 → 必然复现。
- 方案：`Question` 增加 `field_validator('issues', mode='before')`（字符串保留；对象取 message/text/detail；None 丢弃）；`normalize_model_question` 内同步清洗；提示词补充「issues 必须为字符串数组」；可选在 structure 阶段后做一次轻校验。
- 风险：仅 apps/ai/core.py；旧草稿在 /validate 时会被同一 validator 修复。
- 状态：已修（2026-10-21）。`Question` 增加 issues before-validator，`normalize_model_question` 同步清洗，提示词要求字符串数组；对象型 issue 已验证可无损转为字符串。

### QE-FB-014 / P1 自动题框把小节标题框进题目区域

- 现象：题框把「一、单项选择题…」「二、多项选择题…」「三、非选择题…」框进上一题，用户截图任务 `c88aae2e`（物理 章末质量评估（三））第 7 题。
- 根因：`question_span_regions`（apps/ai/core.py:418-423）把每题底边直接对齐「下一题起点」：`bottom = max(content_bottom + .002, next_start)`，中间的小节标题被一并吞入。实测第 7 题内容止于 y=0.314、第 8 题起于 0.371，「二、多项选择题」标题块 0.321–0.364 被完整覆盖（region=[0.518,0.168,0.941,0.371]）。
- 影响面：扫描 12 份 result，23 道题、8 个任务命中；影响题框/裁图/模板/导出，不丢题目内容。
- 方案：先识别「小节标题块」（`^[一二三四五六七八九十]+[、.]` 且含 选择题/非选择题/填空题/解答题/实验题/计算题/综合题），计算底边时取 `min(next_start, 标题块顶边-0.003)`；只截区域，不改进 block_ids/stem；已有任务需重建题框（可加批量重建）。
- 风险：仅 core.py 题框计算；极端版式留 2–3px 空白。
- 状态：已修（2026-10-21）。`question_span_regions` 识别小节标题块并在计算底边时截断（`limit = min(next_start, 标题顶边-0.003)`）；物理卷 Q7 由 0.371 收到 0.318。

### QE-FB-015 / P1 LaTeX 转义修复把 cases 的换行 `\\` 误改成 `\`（公式报错的红字）

- 现象：公式 `a_1=3,a_{n+1}=\begin{cases}a_n+1,&n\text{为奇数},\a_n+2,&n\text{为偶数}.\end{cases}` 中 `\a_n` 非法，MathLive 显示红字；用户反馈该类错误概率高、有时正常。
- 根因（已用缓存对照确认，是程序而非 AI）：
  - AI 原始输出为 `\\a_n`（`\\` 是 cases 的换行 + 下一行 `a_n`），`structure-*.json` 中可见；
  - `normalize_question_content.clean()`（apps/ai/core.py:358）用 `re.sub(r'\\\\(?=[A-Za-z])', '\\', …)` 把「双反斜杠 + 字母」一律收敛为单反斜杠，于是合法的 `\\a_n` 被改成非法的 `\a_n`。
  - 只有换行后紧跟拉丁字母才会中招；紧跟 `&`、`-`、数字、中文的不受影响（同任务第 6 题 `\\-a_n` 完好），所以表现为“时好时坏”。
- 影响面：当前数据中 2 处（任务 `2e502344` 第 4、19 题），已持久化到审核稿；成因对所有含 `cases/array/matrix` 换行的公式都成立。
- 方案：
  1. 收敛规则改为「只在 `\\` + 已知命令名（frac/sqrt/text/begin/end/left/right/…）时去重」；
  2. 跳过 `\begin{cases|array|matrix|aligned|gathered|split}` 到 `\end{…}` 区间（其中 `\\` 就是换行）；
  3. 增加回归用例：`\\a_n` 必须保留、`\\frac{1}{3}` 应收敛为 `\frac{1}{3}`；
  4. 可选：保存前用 KaTeX 做一次非法命令检查，只提示不自动改。
- 数据修复：现有 2 处需把 `\a_n` 还原为 `\\a_n`（或在 cases 环境内做一次性 `\`+字母 → `\\` 迁移）。
- 状态：已修（2026-10-21）。`repair_math_escapes` 改为「双反斜杠 + 已知命令名」才收敛，并跳过 cases/array/matrix/aligned 等环境；`\\a_n` 保留、`\\frac` 收敛。存量 2 处脏数据未自动回改。

### QE-FB-016 / P1 「AI修正N处内容，请核对」不告诉修正了什么，无法核对

- 现象：审核页顶部出现「AI修正1处内容，请核对」，但没有任何修改明细，用户无法核对；同类提示在现有 8 个任务、约 28 道题上出现。
- 根因：
  1. 提示词要求模型记录 `corrections:[{"field":"stem","before":"原文","after":"修正后","reason":"依据"}]`（apps/ai/core.py:649），模型**确实记录了**（可在 `data/tasks/20b31cdf-*/llm/structure-*.json` 看到完整 before/after/reason）。
  2. 但 `Question` 模型没有 `corrections` 字段（core.py:83-111），`Result.model_validate(...).model_dump()` 时被丢弃，落盘 `result.json` 里 `corrections: null`。
  3. core.py:1268 在丢弃前就算出 `correction_count` 并写死成一句通用文案（core.py:1269），所以只剩“N 处”而看不到内容。
- 方案：
  1. `Question` 增加 `corrections: list[dict]`（子问已保留，题目级目前丢失），随审核稿持久化；
  2. 审核页把该提示改成可展开明细：字段 / 修正前 / 修正后 / 依据，逐条列出，提供「撤销此修正」（把 before 写回对应字段）；
  3. 若模型未按要求记录明细，保留“未记录明细”的提示，同时标记该题为待人工核对；
  4. 已有任务可从 `llm/structure-*.json` 按题号回填 corrections（一次性脚本），或本次不追补、新任务生效。
- 风险：`corrections` 只在 pydantic 层新增字段，旧数据缺省为空数组；前端新增一个折叠区，不影响编辑。
- 状态：已修（2026-10-21）。`Question.corrections` 落盘，审核页新增可展开明细（字段/原文/改为/依据）与「撤销此修正」，小问级修正只读展示；存量草稿的 corrections 已在旧版本被丢弃，未回填。

### QE-FB-017 / P0 A3 三栏版面支持（题框/分栏错乱，学生信息区无 A3-3）

- 现象：三栏 A3 化学卷（章末过关检测（一），任务 `e6a43782`）题框错乱：第 1–6 题全部落在 x 0.059–0.342（第一栏），纵向互相重叠（Q3 0.432–0.727、Q4 0.61–0.887、Q5 0.068–0.938 几乎整页）。学生信息区只有 A3-2/A4-1，没有 A3-3。
- 根因：
  1. 分栏是**二值**的：`core.py:400` `column = int((x 中心) > .5)`；`media.py column_bounds` 也用 0.48/0.52 二分。三栏时第 1、2 栏都归入 key=0，第 3 栏归 key=1，导致「下一题起点」跨栏混用 → 题框被别栏的题截断或拉到页底。
  2. 资料里其实已有栏数：该卷 `papers[0].source.columns = [{"page":1,"columns":3}]`（页面 4677×3437），代码未使用。
  3. 学生信息区硬编码 `A3-2`/`A4-1`（main.py:325、336；前端 zoneLayout 联合类型），没有 A3-3 模板。
- 方案：
  1. 分栏改为 N 栏：优先使用 `source.columns` 的 page→columns；缺失时按该页文本块 x 中心找空隙（gap > 0.06）自动推断。
  2. 每栏独立维护 starts 与 column_bounds（该栏全部块的 x 范围），key=(doc,page,column_index)。
  3. 学生信息区增加 A3-3 模板（后端默认 bbox、校验白名单、前端选项），三栏页默认取第 1 栏。
  4. 回归：该化学卷 Q1–Q6 应各归各栏、纵向不重叠；2 栏/1 栏行为保持不变。
- 风险：改动集中在 core.py 分栏 + media.py column_bounds；N=2 时与原逻辑等价。
- 状态：已修（2026-10-21）。分栏改为 N 栏：`page_cells`/`column_index`（优先 `source.columns`，缺失按 x 中心空隙 ≥0.12 推断），学生信息区新增 A3-3；化学三栏卷 Q1–Q4 归第一栏、Q5 跨栏、Q6–Q8 归第二栏。

### QE-FB-018 / P1 解答题题框偏窄，学生作答容易出框

- 现象：解答题（如物理卷 14、15 题）题框只包住文字，右侧作答空白不在框内；学生作答稍偏就会裁到框外，发给 AI 后容易误判扣分。用户目前只能手动拉宽（截图二）。
- 根因：题框 x 范围来自 `column_bounds`（media.py），只统计“该题文本块”的 x 范围（且要求块宽 ≥0.18）；作答空白不是 block，所以框止于文字右缘。纵向已经是“到下一题起点”，横向没有作答空间概念。
- 方案：
  1. 按题型区分：主观题（解答/计算/证明/实验/材料分析/论述）题框 x 取**整栏宽度**（该栏所有块的 min/max 或页栏边界）；客观题保持贴合文字。
  2. 纵向仍到“下一题首块之前”，并留 0.5–1% 安全间距；不得跨栏、不得越过下一题首块。
  3. 可选：区域增加 padding 配置（主观题左右/下 +2%，客观题 0），支持按题型默认值。
  4. 保留人工拖拽覆盖，并把覆盖写入模板层（已有机制）。
- 风险：主观题框变宽可能带入同栏其他内容——用「下一题首块 + 栏边界」双重约束；同栏并排作答区仍需人工微调。
- 状态：已修（2026-10-21）。主观题（解答/计算/证明/实验/材料/论述…）题框横向取整栏 cell 宽度，客观题保持文字贴合；物理卷 Q14/Q15 由文字宽变为整栏 0.51–0.96。

### QE-FB-019 / P2 同栏内相邻题框仍可能重叠（内容块归属交叉）

- 现象：三栏化学卷重建题框后，Q3 [0.43–0.73] 与 Q4 [0.61–0.89] 仍重叠；物理卷 Q14 底边与 Q15 顶边相差 0.004。
- 根因：`question_span_regions` 底边取 `max(content_bottom + .002, next_start)`，当上一题的 block_ids 已包含下一题起点以下的内容时，frame 只能跟随内容延伸；这是 AI 内容块归属（block_ids）交叉，不是分栏问题，已附加「题目框与下一题有重叠」提示。
- 方案：按 next_start 强制截断并标注需人工补框；或用文本首行题号（`^\d+[.．]`）校正 block 归属后再算框。需要先统计交叉比例。
- 决策（2026-10-22，用户）：**保留轻微重叠**。实际作答可能略微溢出，题框下边允许越过「下一题起点」一个小余量（建议默认 0.8%，约 3–4mm，可配置），以提高泛用性；不做强制截断。
- 仍需提示的情况：重叠超过 2%，或本题内容本身已深入下一题（block 归属交叉）时，保留「题目框与下一题有重叠，请核对」提示，不静默处理。
- 状态：已修（2026-10-22，随 028）。下边允许 0.8% 微重叠（`FRAME_OVERLAP_PCT`），超过 2% 才提示；不再强制截断。

### QE-FB-020 / P1 AI 编排阶段模型返回非法 JSON，整任务失败且无法事后定位

- 现象：任务 `47b4bea4-dd3a-457e-8ec2-eb0a5b489890`（26秋 同步解析与测评 历史 必修 中外历史纲要（上）试卷_5-8）在「AI编排 · 结构化」失败：`模型返回的 JSON 无法解析：第 1 行，第 1282 列，Expecting ',' delimiter`；finish_reason=stop、completion_tokens=18460，不是长度截断；用户重试多次仍失败。
- 证据：
  1. `llm/calls/1792629941867-4fb92767.json` 只保存了 system/user/error，**没有保存模型原始输出**，失败现场不可回放，无法确认 1282 列的具体字符。
  2. 结构化调用没有使用 JSON 模式（`response_format` 未传），thinking 处于 enabled。
  3. 解析处只有 `json.loads`，失败直接抛出（core.py:699-705），没有修复、没有自动重试。
  4. 定位时用同参数做了一次真实重放（非高峰约 ¥0.07）：返回 18436 字符、**合法 JSON**，说明是概率性畸形输出，不是这份资料必然失败。
  5. 输入侧检查：user prompt 中没有 ASCII 双引号（中文引号 54/53 对），排除“原文引号未转义”作为固定成因。
- 根因判断：直接原因是该次模型输出在约第 1282 字符处出现了未转义字符（最可能是字符串内 ASCII 双引号或多余转义），使字符串提前闭合，解析器在期望逗号处报错；系统性原因是缺少 JSON 模式、解析容错、失败原文留存和自动重试。
- 方案：
  1. 结构化请求增加 `response_format={"type":"json_object"}`（DeepSeek 支持），保留 thinking。
  2. 解析失败时把原始 content 落盘（如 `llm/calls/{call_id}/raw.txt`，限长），并在错误详情里附“错误位置前后 80 字符”。
  3. 增加轻量修复：去 ``` 围栏、BOM、尾逗号、控制字符；仅在修复后能解析时，才对字符串内未转义的 ASCII 双引号做定向转义。
  4. JSON 失败自动重试 1 次（同参数或降温度），仍失败再落 failed，并在提示里说明已重试次数。
  5. 修正错误语义：当前 `retryable=false` 与“重试会重新调用失败阶段”的提示互相矛盾。
- 影响：一次失败浪费约 11k 输入 + 18k 输出 token；重试没有缓存，成本重复发生。
- 状态：已修（2026-10-22）。DeepSeek chat 增加 `response_format=json_object`（`LLM_JSON_MODE=1` 默认开）；失败调用把原始输出写进 `llm/calls/{id}.json`；解析前做 BOM/尾逗号保守修复；错误信息附错误位置前后 40 字符片段。

### QE-FB-021 / P0 失败任务自动重跑一次，两次失败才判定失败（用户新增需求）

- 需求：任务任一阶段失败时，系统自动重跑一次；两次都失败才标记为失败，避免概率性失败（如 QE-FB-020 的非法 JSON）需要人工点重试。
- 规则设计（待确认）：
  1. 自动重试范围只覆盖“可重试”失败：JSON 解析错误、连接/读超时、HTTP 429/5xx、返回空内容；结构性错误（schema 校验、资料缺失、参数/鉴权错误）不自动重试，避免确定性失败重复计费。
  2. 重试粒度是失败阶段，不是整条任务：已完成阶段复用缓存（structure/answers/match 已落盘的直接读），只对失败阶段重新调用。
  3. 次数：每个任务最多 1 次自动重试；手动“重试”不受限，但会重置自动重试计数。
  4. 状态展示：第一次失败时状态为“自动重试中（1/2）”，并把阶段与原因写进任务 message/事件；第二次失败才落 failed，并保留两次的错误摘要。
  5. 记录：`state.json` 增加 `auto_retry` 计数与每次的 error/usage；成本抽屉能看到两次调用的 token 与金额。
  6. 幂等：重试期间不接受同一任务的重复启动请求，避免并发写同一目录。
- 与 QE-FB-020 的关系：自动重试是兜底，JSON 模式与解析容错才是降概率的正解；两者都要做，否则每次失败都会多花一次 token（约 11k 输入 + 18k 输出）。
- 状态：已修（2026-10-22）。`process()` 失败时若为可重试错误（JSON/超时/429/5xx）且未重试过，写 `auto-retry.json` 标记并 1 秒后自动重跑一次，状态显示「自动重试一次（1/2）」；第二次失败才落 failed。MinerU/阶段缓存照常复用。

### QE-FB-022 / P0 声明栏数错误时分栏仍按 2 栏切：三栏卷第一页全错、第二页正常

- 现象：所有三栏 A3 卷的第一页题框按两栏分布（看起来像双栏），第二页起正常。截图任务为化学《章末过关检测（一）》`0c4e4115`、`e5bbb010`。
- 证据：
  1. `papers[0].source.columns = [{"page":1,"columns":2}]`——模型把首页识别成 2 栏；`attach_page_columns` 原样写入 `doc.columns=[2,None]`。
  2. `page_cells` 优先使用声明值，首页只切 2 个 cell：`[(0.04,0.49),(0.51,0.96)]`；第二页没有声明，几何推断为 3 栏，所以正常。
  3. 首页块的 x 中心分布为 0.18/0.20 一批、0.50 一批、0.75–0.88 一批，相邻间隙 0.30 和 0.25，几何推断结果是 **3 栏**。
- 根因（两段）：
  1. 结构模型输出的是**不分页的标量** `"source":{"columns":2}`（未指明哪一页），本身也不符合“按页给栏数”的契约；
  2. `normalize_paper`（core.py:1128-1136）把标量自动展开成 `[{"page":1,"columns":2}]`，等于程序把“2 栏”硬指派给第 1 页；`page_cells` 又优先信任声明，几何推断（3 栏）被丢弃。
  3. MinerU 只提供内容块坐标，不直接给栏数；栏数完全由模型猜 + 程序解释，缺少几何校验。
- 方案：
  1. 声明只作提示：`page_cells` 先算几何推断，声明与推断不一致且推断 ≥2 时以几何为准，并记录一条提示（如“声明 2 栏，检测到 3 栏，已按 3 栏处理”）。
  1b. `normalize_paper` 不再把标量 columns 展开成“第 1 页”，改为 `columns_hint`（整卷提示），只在几何无法判断时兜底；提示词要求按页输出 `[{"page":1,"columns":3}]`，不确定就不写。
  2. 仅当几何无法判断（块太少、单栏、跨栏大图）时才回退到声明值。
  3. 结构提示词补充：`source.columns` 必须按页面实际栏数输出，A3 允许 2/3 栏，不得默认 2 栏。
  4. 前端“重建全部题框”后可显示每页识别栏数，便于人工确认。
- 影响：所有三栏卷首页；旧任务即使重建题框也会继续错，因为声明优先。
- 状态：已修（2026-10-22）。标量栏数改为整卷口径并应用到所有页；模型看图判断栏数；空白沟几何做交叉校验，不一致时在试卷 issues 留提示。

### QE-FB-025 / P0 双栏被识别成三栏：旧“中心间隙”启发式不可靠，改用空白沟检测

- 现象（用户纠正）：双栏卷第一页正确，后面页会被切成三栏。历史《单元综合评价（二）》任务 `a36d56fd`：4 页 A3 横版，实际每页 2 栏。
- 证据：
  1. 该卷 `source.columns` 只有标量 2 → 程序只给第 1 页声明 2 栏，第 2–4 页无声明，落到旧启发式。
  2. 旧启发式按块 x 中心的相邻间隙 ≥0.12 计数：第 1 页中心为 0.16–0.28 / 0.60 / 0.72，出现 0.32 与 0.12 两个间隙 → 判 3 栏（错）；第 2–4 页同样出现 0.12–0.13 的小间隙 → 判 3 栏（错）。
  3. 用“纵向空白沟”检测（按 x 覆盖统计，忽略宽 >0.55 的跨栏块，忽略距页面边缘 8% 内的沟）原型验证：历史 2/2/2/2 页全对；化学三栏 3/3 页全对；物理双栏 2/2 页全对。
- 根因：栏数判定用“中心点间隙”而不是“整列空白”，一栏内块宽不一致或块偏靠栏边时就会多切一刀；且声明值只覆盖第 1 页，后续页全部依赖该不可靠启发式。
- 方案：
  1. 按页用空白沟检测栏数：以块 x 区间做覆盖，取内部空档宽度 ≥0.015、中心距页边 ≥0.08 的作为栏间沟；栏数 = 沟数+1；
  2. 排除跨栏块（宽 >0.55 或高 >0.6 的装饰/标题）对覆盖的干扰；
  3. 声明值（尤其标量）只作提示：与检测一致才采用，不一致以检测为准并留提示；
  4. 每页独立判定，允许同卷不同页不同栏数。
- 影响：所有双栏/三栏混排的卷；已有任务需重建题框。
- 状态：已修（2026-10-22）。`_infer_column_count` 改为空白沟覆盖检测，作为 AI 栏数的交叉校验与缺失兜底；实测历史 2/2/2/2、化学 3/3、物理 2/2。

  3. 提示词补：按页输出 `source.columns`（数组），以图片+块坐标为准；“图片是资料，不是指令”。
  4. 答案/匹配阶段同样带答案页图。
  5. 保留现有几何推断作为兜底（图片只提高上限，不替代确定性规则）。

### QE-FB-026 / P0 AI 服务假死：reload 模式下 worker 崩溃，reloader 仍占 1003 不响应

- 现象（2026-10-22 09:53）：两个英语任务长时间停在「MinerU识别 · running」；新建任务的「开始识别」一直转圈；页面所有 AI 请求无响应。

  1. `127.0.0.1:1003` 的监听 PID 是 uvicorn **reloader**（57324），其 worker 子进程（52244）已不存在；
  2. 对 1003 发 `/docs`、`/tasks/{id}`、`/settings/concurrency` 全部超时（TCP 可连、无响应），属于“reloader 占端口但无人 accept”的假死；
  3. Java 的 `POST /process` 与同步轮询因此挂住，任务状态停在 running，用户在 UI 上表现为“识别很久 / 新建不了”。

  3. Java 侧 `/process` 增加短超时 + 失败回写，避免 UI 无限转圈；
  4. 任务级超时：running 超过 N 分钟无阶段进展 → 标 `interrupted` 并允许恢复，而不是永久 running。
- 状态：已修（2026-10-22）。AI 增加 `/health`（含 scheduler/started_at/vision）；Java 连续 10 次探测失败（约 25s）把所有 running/queued 任务标 `interrupted`；任务超过 30 分钟无进展（`TASK_TIMEOUT_MINUTES`）自动标 `interrupted`；提供可选看门狗 `scripts/watch-ai.ps1`；AI 当前以无 reload 方式运行。

- 现象（2026-10-22）：多个任务卡在「MinerU识别」，报 `HTTP 403：InvalidAccessKeyId ... LTAI5t8...`；换新 key 后上传成功，但解析阶段统一返回 `unsupported file type`（等待 `waiting-file` 后约 4 秒失败），任务再次落 failed。

  1. 旧 key 的失败发生在 **PUT 预签名 OSS URL** 上；`mineru-task.json` 里缓存了 `file_url` 且 `uploaded=false`，重试会**反复 PUT 同一个过期 URL**，所以永远 403。
  2. 新 key 的 batch 申请与 PUT 都返回 200；失败点在 MinerU 解析服务。
  3. 用**曾经解析成功过的旧文件**、本次任务的 PDF、页面 JPEG、以及现场生成的 9KB 新 PDF 逐一测试，**全部**返回 `unsupported file type` → 不是文件损坏、不是扩展名、不是 A3 版式。
- 已修复（代码）：
  1. 支持多密钥：`MINERU_API_KEYS=key1,key2`（回退单 key `MINERU_API_KEY`），按顺序切换；
  2. 遇到 401/403 或 `InvalidAccessKeyId` 时**删除 `mineru-task.json`**，重新申请上传 URL，不再复用过期 URL；
  3. 每个 key 内最多重试 2 次，失败后换下一个 key，并在任务阶段里提示“第 N 个密钥失败”。
- 进一步证据（2026-10-22，三个新 key 全部测试）：
  1. 三个 key（含用户本人账号）对**同一份 9KB 全新 PDF** 均返回 `unsupported file type`；
  2. 用**公网 URL**（w3c dummy.pdf）调 `POST /api/v4/extract/task`，`vlm` 与 `pipeline` 都返回 `failed to read file` → 与本地文件/上传无关；
  3. 同期 `POST /api/v1/agent/parse/file` 返回 200 并给出 task_id（Agent 轻量通道正常）。
  结论：MinerU **标准解析（v4 Standard API）后端当前不可用**，不是密钥、账号、文件或代码问题；只能等待官方恢复或换解析渠道。
- 处置：三个 key 已写入 `MINERU_API_KEYS`（本人账号优先），服务恢复后会自动轮换；现有三个失败任务在恢复后点「重试」即可。
- 状态：本地代码已修；MinerU 解析被拒需外部确认。

### QE-FB-031 / P1 MinerU 本地部署评估：效率与效果（待验证）

- 本机条件：i5-12400F / 32GB RAM / RTX 2080 Ti 22GB / 磁盘剩余 849GB，满足 `mineru[full]` 的 ≥8GB 显存要求，且余量充足。

- 效率参考（第三方 42 页/文档实测，MinerU2.5-1.2B）：
  | GPU | 每页耗时 | 显存峰值 |
  |---|---|---|
  | T4 16G | 447 ms | ~10GB |
  | V100 16G | 267 ms | ~11.5GB |
  | P40 24G | 323 ms | ~10.9GB |
  | A10G 24G | 182 ms | ~13GB |
  | A100 80G | 164 ms | ~14GB |
  10 页文档显存约 3.2–3.8GB；CPU 模式比 GPU 慢 2.8–5.4 倍。2080 Ti（Turing、22GB）预计介于 V100 与 A10G 之间，教辅 4 页 A3 单份预计 10–30 秒（含模型热启动），稳定后更快。
- 效果判断：云端 SaaS 的 `model_version=vlm` 属 MinerU2.5 系列（2.5-Pro 已上线 SaaS）；本地 4.0 `standard` 档同样是 2.5/2.5-Pro 1.2B 同族模型，理论上效果相当。但**不能假设 100% 等价**：云端可能是更新/更大的 checkpoint、后处理参数不同，必须用同一份卷做 A/B（文本、表格、公式、block 坐标）。
- 兼容性：现有 `normalize()` 已按本地 MinerU 目录结构读取 `*middle.json`、`*content_list.json`、图片，接入只需在 `recognize()` 增加 local provider，输出到 `task/<doc>/raw/` 后复用同一套标准化。
- 风险：Windows 下 CUDA/torch 安装、模型下载约数 GB、首次加载慢、许可为 Apache 2.0 + 附加条件（商用需核对）。
- 建议：先装 `standard` 档并用一份三栏卷 A/B（与云端结果对比文本/坐标/耗时），通过后再做 provider 回退（cloud 主、local 备）。
- 实测（2026-10-22，本机 2080 Ti 22GB，MinerU 4.0 + `MinerU2.5-Pro-2605-1.2B`，standard 档）：
  1. 地理四页 A3 卷：模型推理 11.8s（0.34 页/秒 ≈ 2.9s/页），冷启动整体 53s（含加载模型）；
  2. 输出结构与云端 zip 不同：本地为 `middle_json.json` + `structured_content.json` + `model_output.json`，**没有 `content_list.json`**；现有 `normalize()` 匹配的是 `*middle.json` / `*content_list.json`，需要适配；
  3. 文本对比：本地 3390 字符 vs 云端 4531 字符，差异主要是**选项换行/分组不同**（36 行不一致多为 A./B./C./D. 的分行方式），并非整段丢失；接入后需按块/题目做字段级对比。
  4. 本地模型确认为 `MinerU2.5-Pro-2605-1.2B`，与云端同代。
- 状态：已接入（2026-10-22）。`MINERU_PROVIDER=auto|local|cloud`，auto 先本地后云端；新增 `apps/ai/mineru_local.py`（健康检查、`/v1/file_parse` 取 zip、把 4.x 的 `structured_content.json` 转成 `content_list` 形状）；`normalize` 无需改动；`scripts\dev.cmd mineru` 常驻本地服务（8020、standard、并发 2）；`/health` 返回 `mineru.local_available`。实测：原先卡在 MinerU 的任务 `df5d183b` 用本地解析后完整跑到 ready（19 题）。
