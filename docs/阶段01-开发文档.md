# 智慧教学平台｜阶段01开发文档

版本：v1.1｜日期：2026-10-14｜状态：已确认，阶段01正式开发交接版（单一全栈开发AI）

确认记录：本阶段业务范围、架构基线、后台运营换绑与教师姓名/手机号两项必填已确认。用户选择同一个全栈开发AI完成前后端，可按本文开工，具体依赖补丁版本与接口字段在本文约束内确定。

对应需求：[阶段01需求文档](阶段01-需求文档.md)。需求编号R01—R17用于追踪开发与验收。

## 1. 实现目标与分工

完成运营后台建校、绑定运营人员、教师端人员录入、教师激活登录和多校切换。

| 负责人 | 交付内容 |
|---|---|
| 产品 | 已冻结的业务范围、页面行为、权限规则、验收标准；处理实施中新出现的业务变更 |
| 全栈开发AI | 数据模型、认证与授权、接口、模拟短信、迁移、接口契约、两端页面、表单与反馈、学校切换、人员导入、真实联调、测试、部署说明与验证记录 |

同一个全栈开发AI确定字段名、表结构及接口路径，并检查前后端契约一致性。前端与后端是代码职责，不是两个AI负责人；apps/api、apps/web、模块边界、服务端授权与OpenAPI要求仍需保留。产品文档明确每个接口需要表达的业务信息，不要求开发AI自行改变已确认业务规则。

接口契约应在相应页面和服务实现前约定。每个工作包完成服务端、页面、真实联调与关键验证后，再继续下一工作包；可暂用模拟响应推进页面，但最终必须连接真实API与数据库。不能因为由一个AI开发就省略契约或将前端显示逻辑当作后端授权。

## 2. 架构基线与开发规范（工程师不得自行省略）

### 2.1 架构决策与版本基线

整体采用模块化单体业务API＋独立网页应用。Java服务按业务模块组织；未来AI计算使用独立Python服务。第一阶段不引入微服务治理、Kubernetes、消息队列或分析数据库，也不能把模块化单体写成一个混杂的巨型Service。

| 类别 | 本交接采用的技术基线 | 约束 |
|---|---|---|
| 业务后端 | Java 21 LTS、Spring Boot 3.5.x | 不自行改为Python/Node业务后端或Boot 4.x |
| 构建 | Maven Wrapper | 提交mvnw/mvnw.cmd及Wrapper配置，统一Maven版本 |
| 持久层 | MyBatis-Plus 3.5.x，Boot 3专用starter | 显式SQL留在所属模块；不混用JPA作为第二套持久层 |
| 数据库 | PostgreSQL 17 | 业务schema为jinban；不使用H2替代真实数据库集成测试 |
| 迁移 | Flyway及PostgreSQL支持组件 | 只新增迁移；运行账号与迁移账号分开 |
| 认证基础 | Spring Security，由Boot BOM管理版本 | 只管理认证、会话与基础防护；学校业务授权通过独立策略实现 |
| 会话 | Spring Session JDBC，共享PostgreSQL持久化会话 | 第一阶段不用Redis；不只把会话存在进程内存 |
| 网页 | Node.js 22 LTS、pnpm、Vue 3.5、TypeScript strict、Vite | 精确版本与pnpm版本写入仓库；提交锁文件 |
| 前端组件与状态 | Element Plus、Pinia、Vue Router、Axios | 一个HTTP客户端；教师端与后台使用不同布局和路由守卫 |
| 后续AI服务 | Python 3.12、uv、FastAPI | 本阶段只记模块位置及HTTP契约边界，不搭空AI服务 |
| 部署 | Docker、Docker Compose v2 | 本地数据库容器化，应用可本机运行；交付可构建镜像 |
| 接口 | OpenAPI 3.1 YAML | 契约先行，后端产出；实现与契约持续比对 |
| 质量工具 | JUnit 5、Spring Boot Test、ArchUnit、ESLint、Prettier | 构建必须运行模块边界检查与关键行为测试 |

上述为本次产品与架构规划的交接基线，不声称历史文档的所有技术判断正确。精确补丁版本由后端在骨架阶段选取可获取、兼容且无已知阻断漏洞的版本，前端按Node基线选择兼容依赖；分别锁入pom/BOM、Wrapper和pnpm-lock.yaml。禁止依赖版本写LATEST、使用浮动镜像latest或自动升级主版本。若已无法获取受维护兼容版本，先提交替代决策及影响说明，再改基线。

历史材料中“自定义签名token、不引安全框架”的方案不沿用：本交接使用成熟认证与会话组件，避免将自定义凭证协议变成长期维护负担。未来特殊客户端通过公开认证接口对接，不直接共享浏览器Cookie或数据库会话表。

### 2.3 业务模块地图与所有权

| 模块 | 职责与数据所有权 | 本阶段 |
|---|---|---|
| identity | 登录账号、手机号唯一性、密码、验证码、会话、平台运营资格 | 实现 |
| school | 学校、运营绑定、教师校内信息、校内使用权；以后年级/班级/学生/任职 | 实现当前范围 |
| content | 教辅批次、章节、知识点 | 规划 |
| question | 题目身份与版本、试卷组成 | 规划 |
| assignment | 作业布置与目标、作业状态机 | 规划 |
| scan | 扫描批次、页面、文件元数据、核对结果 | 规划 |
| grading | AI任务业务结果、教师复核、改分审计 | 规划 |
| analysis | 学情计算、错题、重练关联与比较 | 规划 |
| notify | 站内消息、送达状态、通知能力 | 规划 |
| billing | 算力用量、配额、计量事件 | 规划 |

identity提供账号能力，school通过identity.api调用账号查找/创建；identity不import school，不查询学校表。登录响应提供账号主体，前端再调用学校公开HTTP接口取可进入的学校，避免“登录必须知道所有学校”造成反向依赖。

公开接口只暴露稳定ID、值对象、业务DTO或命令，不返回Mapper、Entity、Spring HTTP对象。跨模块导入账号时school调用identity.api参与同一数据库事务；验证码/登录失败审计等独立结果按具体事务语义处理，不能为了复用事务丢失失败留痕。

后续依赖从使用者指向基础数据拥有者：question可用content.api，assignment可用question.api与school.api，scan可用assignment.api，grading可用scan.api与assignment.api，analysis可用grading.api与assignment.api。不要画成scan和grading相互调用。扫描完成后由后续明确的应用编排或事件机制启动批阅，不让scan反向调用grading内部类；第一阶段不建设消息系统。

### 2.4 高内聚、低耦合的具体判据

| 必须做到 | 可检查的实现规则 |
|---|---|
| 一类业务集中 | 一个功能的入口、规则、数据访问与测试位于所属模块，不建立全局controller/service/mapper大平铺 |
| 单向分层 | Controller → Service → Domain/Mapper；Domain不依赖Web、数据库或其他模块实现 |
| Controller职责小 | 参数校验、认证主体获取、调用应用服务、返回DTO；不写SQL、不调用Mapper、不承载导入规则 |
| Service边界明确 | 业务编排与事务，不依赖HttpServletRequest/Response，不返回Entity给浏览器 |
| Mapper只管持久化 | 不发送短信、不决定谁有权限、不修改其他模块表 |
| 跨模块只用公开接口 | 外部只import对方api；禁止import对方service实现、domain实体、mapper、dto内部类 |
| 公用包保持小 | common只放确实跨模块复用的无业务类型，禁止塞教师规则、短信发送、学校权限或巨大Utils |
| 外部服务可替换 | 业务只依赖发送/存储/AI等端口；厂商实现只在infra内部 |
| 状态规则集中 | 校内正常/停用/解除关系的合法变化在domain中表达，服务不散写互相矛盾的状态判断 |

例：改教师本校姓名应落在school.web、school.service、school.domain/mapper及其测试；不修改Account实体，不让Controller调用identity的Mapper。导入手机号已有账号时调用identity.api，再写school拥有的校内记录。

不要求每个简单类都创建无意义接口，不套用完整DDD模板；公开模块契约和外部能力端口必须有接口，模块内部按职责拆分。类过大、同时负责认证/建校/导入等不同用例时必须拆分，不能仅靠增加注释维持巨型类。

### 2.5 学校隔离基础设施

school.access统一提供校内访问与管理资格判定，构造由服务端校验后的SchoolScope。对外供后续模块使用的范围类型与访问契约归school.api所有，实现留在school.access；外部模块不import school.access内部类。校内查询/更新Repository入口要求该范围对象，拒绝未检查的原始schoolId进入持久化流程；Mapper内部仍按school_id约束实际读写，包括主键查询、分页、统计、导入、更新和恢复。

未带学校范围或范围校验失败时默认拒绝，不能默认全校。禁止把“MyBatis分页/租户拦截器已配置”当成原生SQL、多表更新和批量操作安全的证明；每类SQL路径都必须有越权测试。不得假设只在列表加WHERE就足够。

后台跨校查询使用仅由平台运营鉴权产生的PlatformScope，独立入口与审计；不得通过前端布尔参数global=true绕过校内范围。普通教师、本校管理员和后台运营三种上下文必须分开。

未来模块通过school.api取校内访问资格，不读取school内部Mapper；学科、班级、任职时间和敏感内容范围以后扩展为细粒度策略，第一阶段学校管理员资格不能直接成为未来所有教学功能的无条件通行证。

### 2.6 数据库与持久化规范

- 所有DDL和基础约束只走Flyway；已交付迁移不改、不删，新增迁移表达后续变化。不能承诺任何迁移都可自动回滚，回退通过已验证恢复/前向修复方案。
- 迁移用户拥有建表权限，业务运行用户无DDL、无TRUNCATE。生产迁移作为独立部署步骤，业务启动不要求获得迁移权限。
- 表、列使用snake_case；关系由外键约束，禁止依赖“业务层应该不会错”代替物理一致性。
- 技术主键使用bigint雪花ID，配置实例唯一的节点标识并检测重复/时钟回拨；节点分配无法保证时不得盲目上线多副本。JSON中的大整数ID统一作为字符串，避免JavaScript精度丢失。
- 手机号账号唯一；账号与学校一条持续校内记录，正常/停用/解除以状态表达，恢复及重新关联复用记录，不能丢失姓名与审计。解除后的重新关联行为需遵守当前关联状态和导入冲突规则，不自动恢复旧权限。
- 学校允许确认后同名同地区，不能用唯一索引强行拒绝。学段为四项集合，持久化形式由后端在模型说明中明确，不以拼接中文显示串作为授权/检索数据源。
- 时间使用timestamptz，接口用ISO-8601带时区；默认展示Asia/Shanghai。状态字段长度覆盖全部枚举，非自明字段有数据库注释。
- SQL参数绑定，禁止字符串拼接用户输入。姓名、手机号为文本，不转为数字；列表分页、排序字段白名单，关联与过滤字段建立索引，避免N＋1查询。
- 并发改名/停用可用version字段乐观锁，冲突明确返回，不静默覆盖。导入确认阶段重新校验并原子提交；幂等记录与业务写入同事务。
- 审计只追加，记录操作人ID、学校ID、教师校内记录ID、动作、时间、结果和必要的受控差异；访问受授权保护。不把业务审计敏感内容当作普通日志输出。

### 2.7 认证、会话与基础防护

浏览器使用Spring Security认证与Spring Session JDBC持久化会话，Cookie设HttpOnly、Secure、适当SameSite。开发通过Vite代理、部署通过同源反向代理，默认不开放任意来源带凭证访问。保留CSRF保护，前端发送相应token；Cookie路径与会话退出范围必须统一测试。

通过框架PasswordEncoder使用带随机盐的PBKDF2，使用可识别版本/参数的存储格式和常量时间比较；参数经目标机器耗时测量记录，不自写密码加密算法。验证码生成使用安全随机数；数据库只存校验凭证，模拟环境展示值另走受限调试响应，不写一般日志。

会话设有限闲置期及最长有效期；改密后撤销其他会话，退出撤销当前会话。校内停用检查关联最新状态，不全局踢出账号；恢复不生成新密码。认证主体只含账号身份，不能把登录时的全部校内权限长期固定在会话中。

第一阶段会话、验证码、发送频控、幂等与导入预览存共享持久化状态，不靠进程内Map才能工作；后续若压测要求改为Redis，通过持久化端口替换并新增架构决策。多实例下登录、退出、验证码消费和校内停用要有一致行为。

### 2.8 外部能力与后续扩展

短信定义SmsSender端口，模拟实现本阶段启用，Aliyun实现后续审核就绪再启用。阿里云SDK可用于适配内部，不能出现在Controller、Domain或业务Service中，也不能让账号规则依赖某厂商响应格式。旧材料“一律禁用厂商SDK”不直接照搬，采用供应商实现可替换、密钥配置外置的规则。

未来图像文件由文件/对象存储端口管理，业务表只存对象键与元数据，不把全量图片塞进业务行或绑定某云访问URL。AI走HTTP契约与独立计算服务，超时、重试、幂等和人工复核在相关阶段设计；不能在第一阶段登录事务中预埋AI调用。

未来扫描/AI等长任务独立于HTTP请求和数据库长事务，规划任务状态及可靠投递机制；不承诺只靠模块化单体就能达到全部长期吞吐目标。新模块落地前补充容量验证、异步机制和持久化方案，不能未经测量就提前分库分表。

部署按环境配置，省份/合作方部署实例的数据、数据库、短信密钥隔离，不能硬编码广东/贵州分支散落业务逻辑。具体跨省合作形态仍按后续需求决定，不在本阶段实现白标或多租户计费。

### 2.9 前端目录与规范

```text
apps/web/src/
├─ app/                         # 入口、布局、路由及全局初始化
├─ api/                         # 唯一HTTP客户端、契约类型

│  └─ school/                  # 学校/教师/导入/切换

└─ shared/                      # 通用反馈、基础组件与无业务工具
```

页面不直接使用Axios，不复制账号/学校类型，不将所有教师、导入和运营状态塞进一个全局store。后台与教师端不同布局、路由前缀与入口权限；路由守卫不能代替后端授权。TypeScript strict保持开启，不用any逃避契约，组件props有类型。前端不存短信密钥，不以VITE_变量保存任何服务端秘密。

命名：Java类UpperCamelCase、方法camelCase、枚举UPPER_SNAKE_CASE；Vue组件PascalCase.vue、普通TS文件kebab-case.ts。格式与lint检查必须可运行，禁止把关闭检查作为修复报错。

### 2.10 API、异常与可观测性

路径以/api开头，后台运营与校内教师能力在路径及安全配置中明确区分。CRUD使用资源名与HTTP方法，激活、验证码验证等确实为动作的端点可明确命名，不为满足“绝无动词”规则伪造资源。

JSON业务接口采用统一响应：code、message、data、traceId；文件下载使用正确内容类型，不强塞JSON。401表示未认证、403表示无权、400表示参数格式问题、409表示业务/并发冲突、429表示频控、500表示未知故障；业务错误码提供稳定语义。导入校验请求成功处理时可HTTP 200返回含错误列表的校验报告，明确canSubmit=false；不能误表示为已导入成功。

一般日志仅记内部ID、动作、耗时、结果和traceId，不输出姓名、手机号、密码、验证码、token、学生数据或整份文件。保留可排查的异常堆栈，脱敏异常上下文；禁止空catch、吞异常、直接向前端输出SQL/堆栈。认证失败统一提示，权限错误不给跨校敏感信息。

健康检查分存活与就绪，数据库不可用时就绪失败；暴露路径与权限由契约/部署说明记录，不能把全部Actuator管理接口公开。记录接口耗时、数据库连接池、错误率、验证码失败、导入失败等指标，作为后续扩容依据。

### 2.11 架构守卫与质量门槛

第一阶段后端构建必须加入ArchUnit或等效检查，不能留到后续再补：禁止模块循环依赖；禁止外部访问非api包；禁止Controller引用Mapper；禁止Domain依赖Web；禁止common/infra反向依赖业务模块；identity禁止依赖school。配置装配的合理例外只能限定到明确类，不能排除整个模块逃过检查。

权限隔离、校内状态、账号唯一性、导入整批原子性、验证码用途与一次性必须有有效断言的测试。数据库测试用独立PostgreSQL测试数据库，同样由Flyway建立jinban schema，可采用Testcontainers，禁止往开发业务库清空数据。不靠覆盖率数字或空断言证明功能完成。

前端检查类型、lint、生产构建，并对关键登录/导入/多校流程进行联调或浏览器验证；后端OpenAPI语法校验与接口实现比对列入检查，未实现自动语义比对的部分用明确逐接口记录补足，不能只称“契约守卫已完成”。

提交使用Conventional Commits，行为/接口/数据库改动与相关文档一起交付。Java规范参照阿里Java开发手册，Python后续采用Ruff。源码文本统一UTF-8，Java不带BOM；Windows PowerShell 5.1脚本含中文时用UTF-8 BOM或显式编码，不能误把Windows读文件问题变成所有文件格式的普遍限制。

## 3. 数据与约束

| 逻辑实体 | 需要表达的信息 | 约束 |
|---|---|---|
| 账号 | 内部标识、手机号、密码凭证、激活/启停状态 | 手机号全局唯一；账号不绑定单一学校；不存放供各校共用的教师显示姓名 |
| 平台运营资格 | 账号是否具有后台运营资格、运营显示名 | 普通教师无此资格；运营显示名不替代各校教师显示姓名 |
| 学校 | 标识、名称、省市区、学段集合、详细地址、备注 | 学段只能来自四项枚举；至少一项 |
| 学校运营绑定 | 学校、运营账号 | 创建时绑定一人；一人可以绑定多校 |
| 教师学校关联 | 学校、教师账号、本校显示姓名、本校使用权状态 | 业务上“手机号＋学校”唯一定位校内信息；姓名与正常/停用状态按关联独立保存，停用不删除记录 |
| 学校偏好/会话上下文 | 默认或当前学校 | 仅能指向本人有资格进入的学校；按下文会话约定实现 |
| 验证码挑战 | 手机号/账号定位、验证用途、校验凭证、到期时间、使用状态、错误次数 | 激活与重置用途不能混用；验证成功后一次消费 |
| 认证记录 | 已知账号标识、时间、结果、请求追踪信息 | 不记录密码、验证码、完整token |
| 导入任务/结果 | 操作人、学校、提交标识、行号、处理结果 | 可解释每行失败原因；存储形式由后端定 |

手机号用于识别和匹配账号，“手机号＋学校”用于识别教师校内信息。数据库可使用稳定内部ID作为主键，通过账号手机号唯一约束及账号与学校唯一约束实现上述业务规则；这不改变手机号与学校的业务唯一性。姓名更新接口由学校管理人员使用，必须定位目标教师与目标学校的关联，不执行全局账号姓名更新；普通教师自行改名不属于已确认功能。

数据库唯一约束与事务保证并发时也不出现重复账号、重复学校关联。新账号创建和学校关联应作为一致操作；失败不能留下无法解释的半成品。

学校名称与省市区不设联合唯一约束。重复提示确认与请求幂等是不同机制：确认重复风险后允许新学校ID；同一次创建请求重试不能创建多个ID。

手机号不提供修改接口。更正流程只改变目标学校的关联，不重写其他学校的数据，也不把原账号登录凭证迁移到正确手机号的账号。

不为后续教学业务提前创建完整空表体系，保留账号、学校关联与未来任职关系可分离的边界即可。

## 4. 权限实施

| 场景 | 后端检查 |
|---|---|
| 运营后台学校管理 | 当前账号有效且具有平台运营资格；允许跨校 |
| 新增运营人员 | 有效运营账号在后台操作；复用手机号账号并添加运营资格，不修改教师校内姓名 |
| 教师端学校管理 | 当前账号有效且与目标学校有有效运营绑定 |
| 普通教师访问学校 | 当前账号有效，目标学校关联存在且本校使用权为正常；只验证登录成功不够 |
| 校内添加/导入教师 | 先检查运营绑定，再校验文件和处理人员 |
| 解除教师学校关联 | 仅运营后台提供；教师端管理资格不能授权此操作 |
| 教师端修改教师本校显示姓名 | 操作人有效且具备目标学校运营绑定；目标教师属于该校；仅更新此关联，不修改其他学校 |
| 教师端停用/恢复本校使用权 | 操作人具有目标学校管理资格；仅更新目标教师与该校关联状态，不停用登录账号或其他校关联 |
| 学校切换 | 校验目标学校资格，更新上下文；拒绝伪造学校标识 |

同一账号同时具有教师关联和运营绑定时，按入口与操作分别检查资格。前端隐藏按钮仅用于交互，不能作为授权依据。

教师端学校范围检查应有统一机制；运营后台使用独立的跨校管理授权，不能将“所有接口只查当前学校”作为统一规则。

校内停用不使整个账号或其他学校会话失效；后端每次校内请求必须检查关联的最新使用权状态，已有会话不得保留被停用学校的访问权。恢复仅更新本校状态，不创建新账号或新关联、不改密码或姓名。普通教师无权恢复自己，他校管理员不能越权恢复。

解除教师学校关联后，该校旧访问资格失效；账号及其他学校信息保留。运营绑定变更影响管理资格，与独立教师关联分别判定。全局账号封禁不作为本阶段教师维护功能，不得用该接口实现学校管理员的校内停用。

全部教师学校关联均停用时，认证仍可成功，普通教师学校选择不提供可用入口，并显示“暂无可使用的学校，请联系学校管理员”；运营独立拥有的有效学校管理资格仍另行判定。当前页被停用时停止展示该校数据，引导选择其他可用学校。测试需覆盖旧会话凭证直接请求和缓存权限失效。

更换学校绑定运营人员已确认纳入阶段01：后台检查新人员有效运营资格，原子替换绑定；一校保持一名管理人员，旧人员立即失去管理资格，若仍有正常教师关联可继续作为普通教师访问该校，不能错误撤销其独立教师资格。前端显示新绑定人员并刷新管理权限，旧会话请求也必须按新绑定判定。

### 当前学校与多标签页（实施约定）

单校账号直接进入该校；多校账号优先进入上次选择的有效学校，没有有效历史选择时显示学校选择页。切换时保存偏好。每个浏览器标签页保存自己的当前学校上下文，不能通过共享会话变量导致其他标签页请求突然落到新学校；请求携带学校上下文也必须经后端资格校验，不能信任客户端传入值。无学校时显示引导，不伪造学校ID。具体凭证实现由后端确定并写入契约。

## 5. 认证与模拟短信

### 业务流程

初始运营账号：部署配置提供手机号与初始密码，由初始化命令创建；不在迁移或代码中硬编码真实凭证。初始密码首次登录必须修改，重复执行初始化不得覆盖已有账号密码。其他运营账号由后台新增并使用统一激活流程。初始化命令与登录参数要写入交付说明。

首次激活：输入已录入的手机号 → 请求激活验证码 → 测试环境展示验证码 → 服务端验证 → 设置密码 → 完成激活。

忘记密码：输入手机号 → 请求重置验证码 → 服务端验证 → 设置新密码 → 旧会话失效 → 重新登录。

登录：已确认支持手机号＋密码、手机号＋验证码两种方式。验证码登录须使用独立用途；激活、重置和登录的验证码不能跨用途复用。未激活账号走激活流程，不因验证码登录绕过首次设密码。

### 发送适配

服务端将验证码生成/验证与发送服务分离，配置选择模拟发送或阿里云发送。接入阿里云时替换发送适配，不改变账号唯一性和学校权限逻辑。

模拟服务的验证码仅在明确的开发/测试配置下返回给对应测试页面；真实发送模式不返回验证码。正式环境启动检查应拒绝开启模拟模式。页面展示“测试验证码，未发送真实短信”，不向用户声称短信已经发出。

验证码使用随机生成、限时有效、一次性消费和用途绑定。设置发送间隔、单手机号/来源请求限制、最大验证失败次数；具体值由工程设为可配置项，记录默认值并提交接口评审，不需要额外向用户逐项确认技术常量。

验证码错误、过期、已消费和重复点击需要确定响应。发送失败允许明确重试；未知手机号的对外反馈避免泄露账号是否存在。

密码加盐哈希存储，采用受支持的密码哈希实现；不保存明文密码。使用HTTPS、可失效会话，退出、改密后拒绝相应旧凭证；本校停用仅拒绝该校请求，不使其他学校凭证失效。登录失败统一提示，认证失败记录不随业务失败回滚。

### 阿里云接入准备

后续所需：账号资质审核、短信签名、模板审核、发送额度、服务端访问凭证及权限。通过服务端环境配置或密钥管理提供凭证，前端不保存密钥，文档不收集真实密钥。

## 6. 人员添加与Excel导入

手工添加与批量导入调用同一套账号查找/创建、学校关联规则，避免两条链路行为不一致。

模板只包含姓名、手机号，两项必填，其中“姓名”明确表示本校显示姓名；学校由当前操作上下文确定，不依据文件内容切换学校，不增加本阶段未使用的学科/班级等字段。

第一阶段支持.xlsx、固定列名“姓名”“手机号”、姓名与手机号去除首尾空格、手机号按字符串读取，不接受无法恢复的科学计数法或失真数字。纯空行可忽略；非空行缺必填项必须定位错误。格式规则通过模板说明与接口契约明确，不能静默截断或猜测号码。

流程：下载模板 → 上传 → 服务端整批检查 → 返回详细错误或通过预览 → 全部通过后确认提交 → 返回导入结果。有错误的批次不能提交，不允许部分导入。

逐条错误返回原文件行号、字段/列名、错误类别、具体原因、修改建议和适合展示的原值。文件内重复要返回相关行号；同校信息不一致的错误只与当前学校信息比较，返回本次值与本校已有值。文件级错误也要提供可行动原因。前端不得将这些信息压缩成“文件有误”或“导入失败”。

同手机号账号已在其他学校且姓名不同，不判作身份冲突；复用账号，新建目标学校关联并存入本次的本校显示姓名。不得修改其他学校姓名，教师端校验结果也不得泄露其他学校人员信息。

确认提交时重新核验权限、文件/预览版本与数据一致性，防止检查通过后数据库变化导致部分提交；第一阶段教师名单的批次提交使用整批原子事务，有任一行失败时回滚全部账号与关联写入，并返回定位原因。不得先逐行提交成功记录再报告整批失败。

必须处理的情况：格式错误、空行、姓名/手机号缺失、手机号格式错误、文件内重复手机号、已存在账号、已在本校、同校显示姓名差异、越权目标学校、重复提交、并发导入。

文件大小、行数、扩展名与解析限制由工程提出合理配置；文件内容按实际格式检查，姓名和手机号不写入一般应用日志，禁止执行文件里的公式或宏。

### 已确认的重复与冲突规则

1. 先按手机号定位账号，再按目标学校定位教师校内信息，不比较其他学校的姓名。
2. 目标学校尚无关联：复用已有账号或新建账号，再新建校内信息，保存本次姓名。
3. 同一“手机号＋学校”的导入字段完全一致：跳过，不新增记录，也不修改既有信息。
4. 同一“手机号＋学校”的导入字段不一致：返回具体差异错误，整批不写入；不执行自动更新。
5. 文件内完全一致重复行归为一个待导入项，其余标记跳过；同手机号差异重复行全部标记冲突并定位相关行。
6. 有错误时允许展示待新增/待跳过的预览统计，但必须标明尚未导入，实际成功数为0。
7. 无错误时提交新增项，跳过项不改变数据库；全为跳过时返回正常完成及全部跳过结果，不执行新增写入。
8. 提交时重新比较本校数据；若已被其他管理人员修改而产生冲突，拒绝本次整批提交并返回具体原因。
9. 状态不属于导入字段，完全一致重复的停用教师也跳过，不能因导入恢复使用权；恢复由独立的教师端管理操作完成。

当前模板字段为姓名、手机号，比较范围为这两个字段，按上述首尾空格处理后比较。标准化规则必须在契约中定义，不能拿其他学校资料参与比较；新增导入字段须同步更新需求、模板、差异规则和接口契约。

## 7. 接口能力清单

后端产出OpenAPI契约，定义方法、路径、字段、枚举、权限、错误码及示例。下列是业务能力，不是已经确定的接口路径。

| 能力 | 输入/上下文 | 返回内容 |
|---|---|---|
| 登录/退出/当前用户 | 登录凭证或会话 | 当前账号、可进入的端、可访问学校及管理资格 |
| 发送/验证验证码、激活/重置 | 手机号、用途、验证码、密码 | 流程状态；仅模拟环境返回测试验证码 |
| 学校查询、创建、修改 | 筛选条件或学校信息、绑定运营人员 | 学校信息、学段、绑定运营人员 |
| 可绑定运营人员查询 | 搜索及分页条件 | 具备有效运营资格的候选账号 |
| 新增运营人员 | 手机号、运营显示名 | 新增或复用账号、运营资格状态；不改变各校教师姓名 |
| 我的学校、切换学校 | 会话及目标学校 | 当前学校、本人身份与可执行操作 |
| 教师查询、手工添加 | 目标学校、人员信息 | 教师列表或账号复用及关联结果 |
| 模板下载、文件校验、导入提交 | 目标学校、文件/任务标识 | 模板、逐行检查、最终结果 |
| 修改本校显示姓名 | 目标学校及账号/关联标识、新显示姓名 | 更新后的本校显示姓名；不得返回或修改其他学校信息 |
| 停用/恢复本校使用权 | 目标学校及教师关联标识、目标状态 | 更新后的本校使用权状态；教师端学校管理员有权执行 |
| 后台解除关联 | 目标学校及教师关联标识 | 解除结果；教师端管理资格不能执行 |

统一约定分页、时间格式、加载/失败响应。认证失败与权限不足区分处理；前端可按业务错误显示字段级提示。

## 8. 前端交互要求

- 学校表单学段使用多选，保留已选值；运营人员选择支持搜索，不提供联系人或联系电话。
- 创建学校发现同名同地区时，展示候选学校名称、区域及详细地址，提供“取消”和“仍然创建”；继续创建请求明确表达重复风险已确认。重复点击防重不替代服务端幂等处理。
- 后台运营人员列表提供新增入口，运营显示名只用于管理识别；手机号复用不改变账号原密码或任何教师校内信息。
- 所有教师手机号均以只读方式展示，不提供直接编辑；错误号码提示去后台解除对应学校关联后重新添加。
- 后台学校列表与教师端“我的学校”使用不同授权范围。
- 普通教师首页展示学校、本校显示姓名、教师身份；切换学校后从目标学校关联取姓名，不从全局账号信息取姓名。仅有有效管理资格时显示人员管理入口。
- 切换学校时清理旧学校列表、表单及导入上下文；旧请求晚到时不得覆盖新学校页面。
- 导入预览逐项展示原文件行号、字段、原值、具体原因、修改方法及关联错误行；有错误时禁止确认导入，显示“未导入任何人员”。全部通过才显示确认提交入口。
- 教师端学校管理员可在本校教师列表编辑姓名、停用/恢复本校使用权。列表显示正常/停用状态；停用按钮说明“仅影响本校，其他学校不受影响”，恢复后保留姓名。成功后刷新本校列表，不修改其他学校。
- 教师端不展示解除学校关联入口，后端也拒绝仅凭教师端管理资格解除关联；不能用跳转后台替代本端的改名、停用或恢复功能。
- 模拟验证码只在测试模式展示，明确环境提示；正式模式无展示代码入口。
- 提交期间防止重复点击；失败保留可重试的信息；成功后刷新相关列表。
- 无学校、无权限、网络失败、会话过期均有明确反馈。

## 10. 验证与交付

重点验证：并发重复手机号仍只有一个账号、重复校内关联、多校切换、管理人员修改A校教师姓名不影响B校、跨校不同姓名导入正常复用账号、同校一致重复跳过、同校差异重复整批报错无写入、文件内重复与全跳过结果、提交前并发姓名变更导致整批拒绝、后台与教师端授权差异、验证码用途/过期/一次性、改密后的旧会话、正式环境拒绝模拟验证。

校内停用专项验证：停用A校后账号仍可登录并访问B校；A校旧会话凭证请求被拒；恢复A校保留姓名与原关联；全部教师学校关联停用时普通教师显示引导；独立运营管理资格不受教师关联停用误伤；重复导入不恢复；普通教师不能自恢复，他校管理员不能恢复A校教师。

补充验证：新增运营资格复用账号且不改校内姓名、重复建校提示与继续确认、创建请求重试幂等、手机号只读与错误关联重建、多标签页学校上下文、运营换绑后旧管理资格失效而独立教师资格保留、姓名/手机号必填。未实际执行的检查不能在验证记录中写成已通过。

前端验证完整闭环、加载与失败状态、学校切换后的旧响应、表单校验、导入预览与结果、未关联学校引导。

交付：可启动的前后端、环境示例与初始化说明、数据库迁移、与实现一致的OpenAPI、模板、测试/联调结果、已知限制。真实短信未接入时必须注明“仅受控测试可用”，不能宣称真实手机号认证已完成。
